# Security hardening (branch `hardening`, 2026-11-10)

This branch fixes the issues found in an audit of ProxOrchestrator 1.1.2
(`main` + `dev` as of 2026-04-18). Every fix has a regression test in
`apps/core/tests/` (46 tests).

## Critical

| # | Issue | Impact | Fix |
|---|-------|--------|-----|
| 1 | nginx `location /vm-ws/` proxied **any** method/path to the Proxmox API with the API token attached, without authentication | Anyone reaching port 8443 had full Proxmox API access (create/delete VMs, read config, …) | Console proxy is generated by a root helper: only `GET …/(qemu\|lxc)/<id>/vncwebsocket` is proxied, each handshake goes through `auth_request` to Django (`/internal/console-auth/`), which requires a logged-in session that opened that guest's console in the last 120 s. Everything else under `/vm-ws/` returns 404. |
| 2 | allauth's `/accounts/signup/` was open | Anyone on the network could create an account and use the app | Local signup closed (`ClosedAccountAdapter`); `/accounts/*` blocked except the Microsoft OAuth flow |
| 3 | No role checks: any user could change Proxmox settings, browse/create directories on the server and run community scripts as root on Proxmox | Combined with #2: unauthenticated → root on Proxmox | `AccessControlMiddleware`: deny-by-default login, admin-only for `/settings/`, `/users/`, `/wizard/…`, `/admin/`, community-script pages; WebSocket consumers require admin |
| 4 | `/accounts/login/` and `/admin/login/` bypassed MFA | MFA ineffective | Both redirect to `/login/` |
| 5 | Root-terminal WebSockets had no Origin check (cross-site WebSocket hijacking) | A malicious page could drive the root shell with the admin's cookie | `AllowedHostsOriginValidator` |
| 6 | Service user could `sudo tee` nginx config files and owned the nginx include files (which also held the API token in clear text) | Compromise of the app user → root on the ProxOrchestrator server (e.g. `access_log` to `/etc/cron.d`) | `sudo` limited to `/usr/local/sbin/proxorchestrator-nginx-helper`, which validates every argument and writes only fixed templates to root-owned `/etc/proxorchestrator/nginx/` (0600) |

## High

- **Importer path traversal (Proxmox side)**: `storage/delete-proxmox/` and
  `storage/create-from-proxmox/` only checked `startswith(temp_dir)`, so
  `<temp>/../../...` let any logged-in user (not only admins) run `rm -f` as
  root on any file of the Proxmox host, or import another VM's disk into a
  VM they control. Paths are now normalised and `..` is rejected.
- **Entra ID**: blank tenant fell back to `common` (any Microsoft account in the
  world could sign in); Microsoft identities were linked to existing local
  accounts by the user-controlled `mail` attribute (account takeover, and the
  account was switched to "entra", skipping local MFA); errors in the group
  check failed open; `allowed_domains` was shown in the UI but never enforced.
  All fixed (specific tenant required, no linking to local/LDAP accounts,
  fail closed, domains enforced).
- **SSH/SFTP**: `AutoAddPolicy` everywhere and SFTP over a bare `Transport`
  with no host-key check → trust-on-first-use pinning in
  `SSH_KNOWN_HOSTS`; a changed key is refused.
- **Proxmox API TLS**: `verify=False` → certificate SHA-256 pinned on first use.
- **Dependencies**: Django 4.2 (EOL April 2026) and ~180 known CVEs across
  Django, Pillow, cryptography, Twisted, allauth, gunicorn, requests… →
  Django 5.2 LTS and current releases; `pip-audit` clean.
- **No brute-force protection** on login, MFA (TOTP and e-mail code — the
  e-mail code had unlimited attempts) and password-reset requests → Redis-backed
  throttling per user and per IP.

## Medium / low

- Open redirect via `?next=//evil.example` on login and MFA.
- Password-reset links built from the `Host` header with `ALLOWED_HOSTS=*`
  → `PUBLIC_BASE_URL`; wildcard host dropped unless `ALLOW_ANY_HOST=true`.
- App started with a hard-coded `SECRET_KEY` if none was set → refuses to start.
- Missing secure cookie flags, `X-Frame-Options: DENY`, nosniff, referrer policy.
- htmx loaded from unpkg without integrity check (JS injection into the admin
  UI if the CDN is compromised) → vendored `static/js/vendor/htmx-1.9.12.min.js`.
- MFA check failed open on unexpected errors.
- ACME challenge token used as a file name without validation.
- Community scripts restricted to
  `https://raw.githubusercontent.com/community-scripts/ProxmoxVE/main/(ct|vm)/*.sh`.
- Bugs found on the way: login errors were never displayed; WebSocket
  `disconnect()` crashed when `connect()` had rejected the socket; the VNC
  console failed whenever a Proxmox 9 ticket contained `"`, `<` or `>`
  (console data was hand-built JSON inside `<script>` and got HTML-escaped —
  now emitted with `json_script`).

## How it was tested

- 46 regression tests (`python manage.py test apps.core.tests`).
- nginx + gunicorn + a fake Proxmox in a container: with the original
  `/vm-ws/` block an unauthenticated `DELETE /vm-ws/nodes/pve/qemu/101`
  reached the API with the token attached; with the new block it returns 404.
- Full install with the modified `install.sh` on a disposable Debian 13 VM
  running a nested Proxmox VE 9.2, then `update.sh` over it, then an
  end-to-end client (25/25): signup blocked, complete setup wizard (SSH key
  copy, least-privilege token `po@pve` with PVEVMAdmin + PVEDatastoreUser +
  PVEAuditor), discovery, inventory, VNC console reaching the guest (`RFB
  003.008`) only with a session that opened it, `/vm-ws/` API paths 404
  without login, operator blocked from admin areas and the root terminal,
  cross-site WebSocket rejected, login lockout via Redis, SSH host key and
  API certificate pinned (fingerprint matches `/etc/pve/local/pve-ssl.pem`).
- Community-script deployment on a production Proxmox VE 9.2 (2026-11-10),
  Alpine LXC through the deploy form and the live terminal. The first runs
  exposed five problems, all fixed and covered by tests:
  1. every script terminal closed after 5 s (`channels_redis` + redis-py >= 6
     idle `TimeoutError`) — explicit `socket_timeout`;
  2. the core ignores `var_diagnostics` and blocks on a dialog whose default
     is "Yes" — the app writes `DIAGNOSTICS=no` first if no choice exists;
  3. no way to choose the template storage — new form field
     (`var_template_storage`); note the core still asks once per host, on
     its very first run, to create `default.vars`;
  4. the new CT ID was never recorded (current output is colourised
     `Container 104 created`) — ANSI stripped, both formats matched;
  5. after a browser reconnect the DONE/exit notice went to the old socket —
     notices follow the attached socket.
  Final run: no prompts, DONE in 28 s, CT ID recorded. Test containers were
  removed afterwards.
- VM community script on the same host (`debian-vm`, Debian 13): the
  interactive terminal answered 5 dialogs (version, cloud-init, user,
  password, settings), VM created and started in 138 s, VMID recorded;
  VM, cached image and credentials file removed afterwards. Getting there
  exposed three more problems, fixed and tested:
  6. a failed or empty script download (`bash -c "$(curl …)"` on a 404)
     was reported as success — now an error (exit 97);
  7. the VM "refresh catalog" button never worked: its Celery task lived in
     `vm_tasks.py`, which autodiscovery never imports (NotRegistered), and
     the status endpoint crashed with 500 on the failed result;
  8. the shipped catalog was stale (removed scripts such as `debian-13-vm`)
     and every `update.sh` reverted a catalog refreshed in the UI — the
     snapshot is current again and `update.sh` rebuilds both catalogs.
- Disk import on the same host: a real 3 GB VMware Ubuntu 22.04 VMDK
  uploaded by the owner, and a CirrOS 0.6.3 image (SHA-256 verified)
  converted to VMDK and imported through the upload and configure forms.
  The CirrOS VM booted and got a DHCP lease. Findings, fixed:
  9. the converted qcow2 was always kept in the Proxmox temp directory
     (6.6 GB left behind by the 3 GB VMDK) — now an opt-in form option;
  10. `iothread=1` was set with the `virtio-scsi-pci` controller, which
      Proxmox ignores — importer, exporter import and VM creator now use
      `virtio-scsi-single` when iothread is on;
  11. the path traversal described under "High".
  Operational notes: on a small VM `/tmp` is a RAM tmpfs (about half the
  RAM), so set the upload temp directory to a disk path (Settings → Storage)
  and keep about 2× the image size free; VMware guests keep their old NIC
  name in netplan (e.g. `ens160`) and boot without network until it is
  changed to the Proxmox NIC (`ens18`) or to a `match: name: "en*"` rule.
- LXC console on the same host (test container, deleted afterwards): the
  console page issued a ticket; through the authenticated `/vm-ws/` proxy a
  client completed the full RFB 3.8 handshake, VNC authentication with the
  ticket, ServerInit (744x400 "VNC Command Terminal") and a framebuffer
  update; without a session (401) and for another guest's console (403) the
  proxy refused. No app changes were needed.
- Not tested: Entra ID against a real tenant and ACME issuance.

## Upgrading an existing install

`sudo ./update.sh` applies everything idempotently: installs the helper,
rewrites the sudoers rule (validated with `visudo` first), regenerates the
nginx site from the template (backup kept as `*.pre-hardening.bak`), replaces
`ALLOWED_HOSTS=*` with the server's names/IPs, adds `PUBLIC_BASE_URL` and
`CACHE_URL`, deletes the old token-bearing `deploy/proxmox_ws.conf` and
regenerates the console proxy.

After upgrading:

1. Add any DNS name you use to `ALLOWED_HOSTS` in `/opt/proxorchestrator/.env`.
2. Users who are not staff can no longer reach settings, the wizard or
   community scripts — promote administrators in *Settings → Users*.
3. Entra ID: enter your tenant GUID or primary domain.
4. If the Proxmox host is reinstalled or its certificate changes:
   `sudo -u proxorchestrator /opt/proxorchestrator/venv/bin/python /opt/proxorchestrator/manage.py forget_proxmox_hostkey <host> --port 22`
   (and `--port 8006` for the API certificate).

## Recommended Proxmox setup

Do not use a `root@pam` token. Create a dedicated user and a token with only
the privileges you need, e.g. `PVEVMAdmin` + `PVEDatastoreUser` on `/`, with
privilege separation enabled. Note that community scripts and disk import
still use SSH as root on the Proxmox host — enable them only if you need them,
and keep ProxOrchestrator on a management network, never exposed to the
internet.

## Still open / out of scope

- TOTP codes can be replayed within their 30–60 s window.
- Community scripts download further code from the `main` branch at run time;
  they cannot be pinned to a commit from here.

## Fresh installs: no well-known admin password

Upstream used `Password!` as the first-run password whenever the installer's
password prompt was left blank (and always in the LXC one-liner, which runs
without a terminal). Anyone on the network could log in first and take the
admin account. `install.sh` now generates a random password in that case,
prints it at the end, stores it in `/root/proxorchestrator-admin-password.txt`
(mode 600) and still forces a change on first login. `Password!` passed via
`PROXORCHESTRATOR_ADMIN_PASS` is treated the same way. The installers now
clone this fork (`hardening` branch) instead of the unpatched upstream.
